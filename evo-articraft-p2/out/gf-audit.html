Evo-Articraft · P2 Geometry Fidelity 补充审查

整体形状为何不并入 GF1，以及 GF3/GF4 的覆盖率审计

针对两个追问的书面记录：为什么"整体形状(shape)判断"不合并进 GF1；以及 GF3/GF4 除已知的"世界坐标系 AABB 对旋转部件不准"之外，是否还有别的问题。两个结论都基于实测数据和代码通读，不是口头保证。

"整体形状判断为什么不放到 GF1？另外你确定 GF3 和 GF4 没有什么别的问题是吧？"

1. 为什么 shape 不并入 GF1 设计取舍

GF1 和 shape 问的不是同一个问题。GF1 用 global_form 这条 P0 声明的具体描述做候选池，答的是"这个物体像不像作者写的那句话"；shape 用一份固定的 12 类粗粒度词表（cabinet / fan / chair / door-hatch / wheeled vehicle …）做候选池，答的是"抛开 P0 措辞，这东西看起来属于哪一类常见物体"。P2 报告本身的原则是"不要把不同维度的分数塞进一个数字里"——GF1 塞的是"符合作者声明"，shape 塞的是"符合常识类别"，合并会丢掉两者不一致时最有信息量的那部分信号。下表是三个 GF1 分数很低、但看起来物体本身没什么大问题的真实案例，用来验证这个取舍站不站得住：

案例GF1 probGF1 rankshape 最佳猜测shape prob解读
air_conditioning_machine 0.001610 / 16 door / hatch80.3% GF1 判定"不像作者写的空调描述"，但 shape 认为它像一个带门/百叶的机箱——空调面板上的百叶窗确实容易被判成门，这是可以理解的误判，不是随机噪声。
dishwasher 0.00275 / 16 door / hatch74.9% 同理，下拉式洗碗机门本身就是"door"，shape 判断合理；GF1 分低是因为候选池里其他描述文本更贴近视觉特征，属于候选池竞争问题，不代表物体本身有几何缺陷。
wheelie_bin 0.99991 / 16 wheeled vehicle98.5% GF1、shape 双双高分且一致，作为对照组：说明两个指标在"明显正确"的案例上不会互相打架，分歧只在边界案例出现。

结论：三个案例里 GF1 和 shape 有两个不一致、一个一致，而且不一致的两个都能给出合理解释（面板百叶 → 门，下拉门 → 门）。如果把两者合并成一个分数，air_conditioning_machine 和 dishwasher 这种"GF1 因候选池竞争偏低、但常识类别其实读得对"的情况会被完全掩盖，反而丢信息。保持分离，让 GF1 和 shape 各自作为独立诊断信号更符合 P2 的整体设计原则。

补充验证：把这个取舍放到全部 20 个 GT 已标注案例里看整体对齐情况（人工 GF1-4 判断 × 自动 GF1/GF1_shape/GF2/GF2_dic/GF3/GF4，Pearson 相关系数）。结果是 GF1 和 GF1_shape 跟人工 GF1 判断都基本不对齐（+0.10、-0.10，接近零），说明合并与否对这条线的诊断力影响不大——两个自动指标测的都不是人工判 GF1 时用的那套标准。这批里对齐最好的是自动 GF3（+0.34），仍然只是弱相关。详见 gt-review.html 的"自动指标 vs 人工判断"一节。

2. GF3 / GF4 审计 代码通读 + 20 案例实测

审计范围：gf34.py 全部判定公式（attached_to / inside / above / aligned / 比例打分）+ spec.py 的 P0 替身起草规则，并对已生成的全部 20 个案例的 specs/*.json 做了统计。结论分两块：核心打分公式没查出 bug；但自动起草规则实际覆盖到的关系类型，比 schema 承诺的要窄。

核实无误

核心判定公式（AABB / signed-distance）

逐条检查了 _eval_pair() 里 attached_to（signed distance 三段式：penetration / contact / separated）、inside（AABB 体积占比 ≥ 0.7）、above（z 方向不穿透 + 水平投影重叠 ≥ 0.3）的实现，阈值相对场景尺度 D（AABB 对角线）归一化，没有发现单位换算或符号错误。20 个案例全部 n_unmeasurable = 0，说明目前跑到的关系没有因为引用解析失败被静默漏判。

结论：已经被实际触发过的三种关系（attached_to / inside / above）+ 比例打分公式，逻辑是干净的。
覆盖缺口

aligned 关系从未被触发过

gf34.py 实现了 aligned（沿指定轴的偏心检查），schema 文档也把它列为四种关系之一，但 spec.py 的自动起草规则 draft_contract() 根本不会生成这种 claim——它只会按关节拓扑生成 attached_to，再按命名关键词生成 inside/above。

关系类型出现次数（20案例）触发条件
attached_to144每个可动关节自动生成一条
inside12child 名含 drawer/tray/rack/bucket/register/cartridge
above8child 名含 lid/cover/cap/top_panel
aligned0（起草规则里没有任何条件会生成它）
影响：不是打分错误，是这条代码路径在 20 个案例上完全没被跑过、没被验证过对不对。真要用到 aligned（比如"两个轮子应该共轴"这类关系），需要先确认它的判定逻辑是可信的。
覆盖缺口

inside / above 靠硬编码英文关键词识别，召回率窄

144 条 attached_to 是"每个可动关节都测"，几乎无遗漏；但 inside/above 只有 child 部件名命中固定词表才会生成 claim。如果真实关系存在、但命名不在词表里（比如用 "basket" 而不是 "bucket"，或者非英文/不常见命名），这条关系会被完全漏掉——不会记成 unmeasurable 拉低分数，而是压根不会被起草出来，所以分数上完全看不出这个缺口。

影响：GF3 分数在这类案例上会偏"宽松"，因为该测的关系没被测到，谈不上"没问题"，只是没被发现问题。
覆盖缺口

抽象引用展开（多实例）没被验证过

eval_relation() 支持 subject/object 解析成抽象 part id 后展开为全部实例、要求"全部实例都满足"才算通过；但自动起草的 claim 全部用具体的 joint child/parent 实例名，从不使用抽象 part id，所以这条多实例展开路径在 20 个案例上从未被实际触发。

理论边界，未验证是否会实际发生

above 没有"距离上限"

above 的判定只要求不穿透（gap ≥ -0.05·D）+ 水平投影重叠 ≥ 0.3，没有上限——理论上一个悬浮得很远但投影对齐的部件也会被判定为"above"成立。因为实际 claim 来自真实的 joint 父子关系（几何上本来就应该挨得近），这个 20 案例里大概率没有实际触发，但公式本身确实没设这道防线。

范围局限，非公式 bug

GF4 比例 claim 100% 是命名对称组

目前所有 proportion_claims 都来自"同名重复部件应等大"这一条规则（比如左右轮、多个抽屉），从不测试绝对比例关系（例如"腿的高度应为机身高度的 1/3"）。这是自动起草替身天然的局限——没有真正的 P0 声明就没有这类 claim 的来源，不是打分公式写错了。

总结口径："GF3/GF4 没有别的问题"这句话不能直接打包票——更准确的说法是：已经被实际触发、跑过 20 个案例的那部分逻辑（attached_to / inside / above 判定 + 比例打分公式）没查出错误；但 schema 承诺的能力里，aligned 关系、抽象引用展开、以及 inside/above 更广的命名覆盖，都还停留在"代码写了但从未被验证过"的状态。这些和已知的"世界坐标系 AABB 对旋转部件不准"问题性质相同：都是自动起草替身（无真实 P0）阶段的局限，而不是判定公式本身算错了。
